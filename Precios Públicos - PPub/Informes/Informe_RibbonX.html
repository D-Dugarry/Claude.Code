Bugs

Alto

R1 · InvalidateControl con un ID de grupo que no existe en el Ribbon real

VBA_Moduls/M_90_Rutinas_Menú_Aux.bas — Rut_Chg_Usuario, líneas 61-67

El XML real del Ribbon define el grupo como ChangeUser_Group, pero el código pide invalidar "GroupChangeUser" — ID que no existe en ningún control cargado. IRibbonUI.InvalidateControl lanza un error runtime si el ID no existe, y ninguna capa intermedia (Rut_Chg_Usuario, RuT_Ejecutar_Rut, OnAct_ChangeUser) tiene On Error.

Antes
Sub Rut_Chg_Usuario()
Debug.Print "Rut_Chg_Usuario"
    Form_Usuario.Show
    Call RuT_Load_Task_Data("Rut_Chg_Usuario")
    MyRibbon.InvalidateControl "Btn_ChangeUser"
    MyRibbon.InvalidateControl "GroupChangeUser"    '- ID inexistente en el XML real
End Sub
Después
Sub Rut_Chg_Usuario()
Debug.Print "Rut_Chg_Usuario"
    On Error GoTo ErrHandler
    Form_Usuario.Show
    Call RuT_Load_Task_Data("Rut_Chg_Usuario")
    Call Rut_Filtrar_Tareas                          '- recalcula qué botones ve el NUEVO usuario
    If Not MyRibbon Is Nothing Then
        MyRibbon.InvalidateControl "Btn_ChangeUser"
        MyRibbon.InvalidateControl "ChangeUser_Group"    '- *** ID correcto, según customUI14.xml ***
    End If
    Exit Sub
ErrHandler:
    Debug.Print "Rut_Chg_Usuario - ERROR " & Err.Number & ": " & Err.Description
    Call RefreshRibbon    '- red de seguridad
End Sub

Impacto: al cambiar de usuario (acción muy frecuente en un libro compartido), Excel muestra un runtime error justo saliendo del login. El error corta la ejecución antes de que OnAct_ChangeUser pueda llamar a RefreshRibbon, así que la etiqueta de usuario, la pestaña "Boss" y la visibilidad de botones se quedan mostrando el usuario anterior hasta que otra acción cualquiera fuerce un refresco completo.

Alto — riesgo de compilación

R6 · Variable no declarada usada como identificador (sin comillas) dentro de Range(...)

VBA_Moduls/M___RibbonUI.bas — Sub OnAction_Dynamic_Task, líneas 1474-1490

APP_Task_Index se usa 3 veces sin comillas (como identificador VBA) dentro de Prog__APP.Range(...). No está declarado en ningún sitio del proyecto (verificado por grep en los 120 ficheros). Con Option Explicit activo esto debería ser un error de compilación — en todas las demás llamadas del proyecto se escribe siempre Prog__APP.Range("APP_Task_Index"), entre comillas.

Antes
Prog__APP.Range(APP_Task_Index) = Val(Right(control.Tag, 2))
Rutinas_Name = Prog__Menú_Aux.ListObjects(1).DataBodyRange.Cells(Prog__APP.Range(APP_Task_Index), 3)
...
Prog__Menú_Aux.ListObjects(1).DataBodyRange.Cells(Prog__APP.Range(APP_Task_Index), 5) = Prog__APP.Range("APP_Task_Inf")
Después
Prog__APP.Range("APP_Task_Index") = Val(Right(control.Tag, 2))
Rutinas_Name = Prog__Menú_Aux.ListObjects(1).DataBodyRange.Cells(Prog__APP.Range("APP_Task_Index"), 3)
...
Prog__Menú_Aux.ListObjects(1).DataBodyRange.Cells(Prog__APP.Range("APP_Task_Index"), 5) = Prog__APP.Range("APP_Task_Inf")

Impacto: que el libro funcione hoy probablemente se deba a que VBA no recompila el proyecto completo cada sesión (p-code preexistente). Basta con abrir el editor VBA y pulsar Debug → Compilar VBAProject (o editar cualquier línea de este módulo) para que salte — bloqueando potencialmente todas las macros del libro. Recomiendo verificarlo cuanto antes con ese mismo comando.

R9 · Ausencia sistemática de On Error en ~34 de los ~40 callbacks del Ribbon

VBA_Moduls/M___RibbonUI.bas — todo el módulo

Solo 6 callbacks tienen On Error, y limitado al error COM de "Office ocupado" al mostrar Form_Running_Rut — no como protección genérica. El resto (OnAct_ChangeUser, OnAct_Reset, OnAct_Import_*, OnAct_ReCalculate_ListObj_Sht, OnAction_Dynamic_Task...) no tiene ninguna. Un error runtime dentro de un callback del Ribbon es una causa documentada de que la cinta deje de responder a los clics hasta reiniciar Excel.

Patrón actual (repetido en ~34 callbacks)
Sub OnAct_ChangeUser(control As IRibbonControl)
Debug.Print "OnAct_ChangeUser"
    Call RuT_Ejecutar_Rut("Rut_Chg_Usuario")
    Call RefreshRibbon
End Sub    '- sin ninguna protección frente a errores runtime
Patrón propuesto a aplicar sistemáticamente
Sub OnAct_ChangeUser(control As IRibbonControl)
Debug.Print "OnAct_ChangeUser"
    On Error GoTo ErrHandler
    Call RuT_Ejecutar_Rut("Rut_Chg_Usuario")
    Call RefreshRibbon
    Exit Sub
ErrHandler:
    Debug.Print "OnAct_ChangeUser - ERROR " & Err.Number & ": " & Err.Description
    MsgBox "No se ha podido cambiar de usuario:" & vbCrLf & Err.Description, vbExclamation, "RibbonX"
    On Error Resume Next
    Call RefreshRibbon        '- intenta dejar el Ribbon en un estado consistente aun tras el error
    On Error GoTo 0
End Sub

Mejoras de eficiencia y mantenibilidad

M1-M2 · Código muerto

Dos callbacks que nunca se disparan desde ningún control real

M1: GetVsbl_TabProgMenu (líneas 850-853) es un duplicado exacto de GetVsbl_ProgButtons, pero ningún control del XML usa getVisible="GetVsbl_TabProgMenu" — la pestaña Boss usa realmente GetVsbl_ProgButtons. M2: OnAct_RibbonVisible (líneas 817-828) compara contra IDs ("CellCtxtRibbonXVisibilityNone/Min/Max") que no existen en el XML, y es el único sitio que compara por control.ID en vez de control.Tag.

Recomiendo eliminar ambos, o dejar un comentario explícito de "no usado" para que nadie confíe en ellos pensando que protegen algo.

M3 · Limpieza

Más de 100 líneas de código comentado que deberían vivir solo en el control de versiones

Líneas ~750-830 y ~1388-1444: Subs completos comentados (GetLbl_GroupMails, OnAct_MailRDT_Plan, OnAct_Mails, versiones antiguas de Func_TagVisible/GetVisible...). Ya hay git para recuperar historial; se pueden borrar sin perder nada.

M4 · Mantenibilidad

Lógica de visibilidad duplicada en vez de aprovechar la tabla Tb_Tareas

El módulo ya demuestra dos estilos en paralelo: el "genérico" (vía Func_CtrlTab_View, que lee Tb_Tareas) usado por ~15 controles, y el "hardcodeado" (Select Case/If inline) usado por GetVsbl_RibbView, GetVsbl_SheetProtect, GetVsbl_SW_PruebaONOFF, etc. Cambiar cualquier matiz de visibilidad de estos últimos obliga a tocar VBA y volver a exportar/compilar, mientras que los "genéricos" solo requieren editar una fila de Tb_Tareas.

Propuesta: extender la tabla (añadiendo columnas si hace falta, p. ej. una de "Enabled" o de "IDs a invalidar tras ejecutar") para migrar también los casos hardcodeados al mecanismo genérico.

M5 · Fallo en silencio

Func_CtrlTab_View no avisa cuando un Tag no se encuentra en la tabla

Antes
Function Func_CtrlTab_View(Ctrl As String)
    Dim Cont_Row As Integer
    With Prog__Menú_Aux.ListObjects(1).DataBodyRange
        For Cont_Row = 1 To .Rows.Count
            ...
            If Ctrl Like MyTag Then
                Func_CtrlTab_View = SW_Tag_Visible
                Exit Function
            End If
        Next Cont_Row
    End With
    '- si no encuentra ninguna fila: devuelve Empty en silencio, botón invisible sin rastro
Después
Function Func_CtrlTab_View(Ctrl As String) As Boolean
    Dim Cont_Row As Integer
    With Prog__Menú_Aux.ListObjects(1).DataBodyRange
        For Cont_Row = 1 To .Rows.Count
            ...
            If Ctrl Like MyTag Or Ctrl Like MyTag & "_Separ" Then
                Func_CtrlTab_View = SW_Tag_Visible
                Exit Function
            End If
        Next Cont_Row
    End With
    Debug.Print "Func_CtrlTab_View - AVISO: Tag '" & Ctrl & "' no encontrado en Tb_Tareas, se oculta por defecto"
    Func_CtrlTab_View = False
End Function

Su hermana Func_STip_CtrlTab_Value sí avisa ("¡ Control.Tag, NO encontrado !"). Si una fila de Tb_Tareas pierde su Tag por edición manual, el botón desaparece hoy sin ningún rastro.

M6 · Rendimiento

Func_CtrlTab_View recorre la tabla fila a fila en vez de usar Match

Sus hermanas Func_STip_CtrlTab_Value/Func_Rut_CtrlTab_Value ya usan Application.Match, pero esta —que se ejecuta muchas más veces, porque getVisible se llama por cada control cada vez que se invalida el Ribbon— hace un bucle manual con Like fila a fila. Con 65 filas y ~15 controles con este callback, cada RefreshRibbon completo supone varios cientos de comparaciones evitables.

Propuesta: sustituir por Application.Match, manteniendo aparte el caso especial del sufijo _Separ (dos Match, o comprobar primero sin sufijo).

M7 · Rendimiento

Invalidate (refresco completo) usado donde bastaría InvalidateControl de un botón

RefreshRibbon (que hace MyRibbon.Invalidate, invalidando toda la cinta) se llama tras casi cualquier cambio puntual: OnAct_RibbView, OnChange_EditBoxACont, OnAct_SW_PruebaONOFF... Cada invocación obliga a Excel a re-ejecutar todos los callbacks getVisible/getLabel/getEnabled de ambas pestañas y los dos menús contextuales.

Antes
Sub OnAct_SW_PruebaONOFF(control As IRibbonControl)
Debug.Print "OnAct_SW_PruebaONOFF"
    Prog__APP.Range("SW_Test") = Not Prog__APP.Range("SW_Test")
    Call RefreshRibbon    '- invalida TODA la cinta por un cambio de 2 botones
Después
Sub OnAct_SW_PruebaONOFF(control As IRibbonControl)
Debug.Print "OnAct_SW_PruebaONOFF"
    Prog__APP.Range("SW_Test") = Not Prog__APP.Range("SW_Test")
    MyRibbon.InvalidateControl "BtnSW_PruebaON"
    MyRibbon.InvalidateControl "BtnSW_PruebaOFF"

La excepción legítima es OnAct_Goto_Sheet_Sht (bug R7): ahí sí conviene refresco completo, porque cambiar de hoja activa afecta a múltiples grupos distintos.

M8 · Rendimiento menor

Rut_Filtrar_Tareas reordena la tabla de 65 filas en cada activación de hoja

Se invoca desde 16 Worksheet_Activate distintos más OnLoad_MyRibbon, y siempre empieza reordenando Prog__Menú_Aux.ListObjects(1) — aunque el filtrado de visibilidad no depende de ese orden (solo lo usa el listado humano de Form_Menu).

Propuesta: separar el reordenado para que ocurra solo al abrir Form_Menu o tras un RibbonRefresh explícito, no en cada cambio de hoja.

M9 · Higiene

Casing inconsistente entre el XML y el nombre real del Sub

customUI14.xml usa onAction="OnAct_MenuAUX" mientras el Sub real se llama OnAct_MenuAux. Funciona porque VBA no distingue mayúsculas/minúsculas al resolver nombres, pero confunde al buscar por texto exacto (incluso llevó a un falso positivo en el propio análisis antes de re-verificar). Recomiendo unificar el casing en ambos sitios.

M10 · Límite silencioso

El menú dinámico "Short Rut." falla en silencio si Tb_Tareas supera 99 filas

Func_xmlGen genera tags con formato de 2 dígitos fijos (Format(Cont_Row, "00")), y OnAction_Dynamic_Task extrae la fila con Val(Right(control.Tag, 2)). Con las 65 filas actuales no hay problema; con más de 99 filas, solo se leerían los 2 últimos dígitos, apuntando a una fila equivocada sin aviso.

Bajo riesgo hoy, pero merece un comentario o pasar a Format(Cont_Row, "000") con margen antes de que la tabla crezca.

¿Reprogramar M___RibbonUI.bas desde cero?

No lo recomiendo. El fichero es grande (~1500 líneas) pero no está mal estructurado de fondo: ya separa claramente TabUserMenu/TabProgMenu, y ya tiene un mecanismo genérico basado en tabla (Tb_Tareas vía Func_CtrlTab_View) que demuestra que la idea correcta ya estaba ahí. Reescribir desde cero un componente que hoy funciona en producción (salvo las excepciones puntuales de este informe) es el escenario de mayor riesgo/beneficio peor: regresiones sutiles en decenas de rutas de negocio a cambio de limpieza estética.

Recomiendo en su lugar un refactor dirigido, en capas, sin tocar el diseño general:

  1. Corregir primero los 10 bugs de este informe — son quirúrgicos, de 1 a 10 líneas cada uno.
  2. Extender el patrón "tabla de configuración" (M4) a los casos hoy hardcodeados, añadiendo una columna InvalidateIDs con los IDs a refrescar tras cada tarea, eliminando los literales sueltos que causaron R1/R2/R7.
  3. Centralizar los IDs válidos del Ribbon en constantes públicas generadas una vez a partir del XML real (Public Const ID_ChangeUser_Group = "ChangeUser_Group"...), para que un cambio de ID rompa la compilación en un solo sitio en vez de fallar en tiempo de ejecución dentro de un callback.
  4. Envolver InvalidateControl en un wrapper seguro (ver más abajo) y sustituir todas las llamadas directas — esto por sí solo habría neutralizado R1, R2 y R7.
  5. Aplicar On Error (R9) de forma sistemática a los ~34 callbacks que hoy no lo tienen — mecánico, Sub a Sub.
  6. Mover el refresco Ribbon-en-Worksheet_Activate (hoy repetido en 16 .cls, ver R10) a un único Workbook_SheetActivate/SheetDeactivate en ThisWorkbook.cls.
Sub Rut_Ribbon_InvalidateSafe(ByVal ControlID As String)
    If MyRibbon Is Nothing Then Exit Sub
    On Error Resume Next
    MyRibbon.InvalidateControl ControlID
    If Err.Number <> 0 Then
        Debug.Print "Rut_Ribbon_InvalidateSafe - AVISO: ID '" & ControlID & "' no válido (" & Err.Description & ")"
        Err.Clear
    End If
    On Error GoTo 0
