# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué hace este proyecto

App de escritorio (tkinter, Windows) que convierte **un** PDF "Listado de Liquidación de Tasas Académicas de Matrícula" (Universidad Permanente UPUA, Universidad de Alicante) a un fichero Excel con dos hojas:

- **Resumen** — una fila por alumno/expediente, con importes agregados.
- **Detalle** — una fila por línea de cobro (Referencia/Fecha/Importe/Plazo/Forma Pago) **más una fila adicional por alumno** con el importe administrativo en la columna `Imp.Adm.` (esa fila deja vacías las columnas de cobro, porque el cargo administrativo no es una línea de cobro). Así cada importe — cobros y administrativo — tiene su propia fila para conciliar uno a uno.

La app procesa un único PDF por ejecución (no hay cola multi-fichero). Además incluye **dos modos de comparación** entre dos listados del mismo curso (anterior vs. nuevo), cada uno con su botón en el bloque Selección: **"⚖ Comparar Resumen"** (tabla de diff con los alumnos cuyo importe cambió; ver `pdf_compare.py`) y **"⚖ Comparar Detalle"** (las tablas de Detalle de ambos PDF lado a lado, sin diff; ver ambos paneles en Arquitectura).

## Comandos

```bash
pip install -r requirements.txt
python Convert_PDF_Liquid_EP_to_Excel.py      # lanzar la app
python -m py_compile *.py                      # comprobación rápida de sintaxis
```

No hay suite de tests automatizada. La lógica de parseo (`pdf_parser.py`) se validó manualmente contra los dos PDF de muestra de `PDF_Liquidaciones/` comparando la suma de importes netos calculados con la línea `IMPORTE TOTAL POR TASAS` que trae el propio PDF (coincide exactamente: 205.649,00 €, 1645 registros, 206 páginas, 0 líneas sin clasificar). Al tocar `pdf_parser.py`, repetir esa comprobación:

```python
from pdf_parser import parse_pdf
records, paginas = parse_pdf("PDF_Liquidaciones/_237_1365588_Tasas202526.pdf")
print(len(records), paginas, round(sum(r.importe_neto for r in records), 2))
# Esperado: 1645 206 205649.0
```

Y para la hoja Detalle (fila extra de Imp.Adm.), el número de filas debe ser exactamente `nº_referencias_totales + nº_registros + 1` (cabecera), y la suma de la columna `Imp.Adm.` debe coincidir con `sum(r.administrativo for r in records)`.

## Arquitectura

Cuatro módulos independientes (sin dependencias circulares) más la UI:

- **`pdf_parser.py`** — extrae los datos del PDF con `fitz.get_text("text", sort=True)` (PyMuPDF) y regex sobre las líneas resultantes. `Registro` (un alumno) contiene una lista de `Referencia` (una por línea de cobro) más `importe`, `administrativo` e `importe_total_pdf`. **`importe_neto` se calcula siempre como `importe - administrativo`**, nunca se confía en el campo "Importe Total" tal cual lo trae el PDF, porque ese campo viene en blanco en ~0,6 % de los registros (defecto real del informe origen, no de la extracción — verificado con `fitz`; cuando sí trae valor, coincide al 100 % con el cálculo). Expone `parse_pdf(path)` (un fichero; no hay variante multi-fichero) y `corregir_alineacion(records)` (ver más abajo).
- **`excel_export.py`** — vuelca una `list[Registro]` a `.xlsx` (hojas Resumen + Detalle) con `openpyxl`. No conoce nada de PDF ni de tkinter. La hoja Detalle escribe, por cada alumno, una fila por `Referencia` y luego una fila extra solo con `Exped/DNI/Nombre/Imp.Adm.` (columnas de cobro vacías). También expone `export_rows_to_excel(headers, rows, output_path, *, sheet_name, table_name, money_cols, int_cols, count_col)` (una sola hoja, usado por "Exportar Excel" del panel Comparar Resumen) y `export_multi_sheet_to_excel(sheets, output_path, *, money_cols, int_cols, count_col)` (`sheets: list[(nombre_hoja, headers, rows)]`, una hoja por tupla en el mismo libro; usado por "Exportar Excel" del panel Comparar Detalle para volcar las tablas A y B en dos hojas, "Detalle A"/"Detalle B"). Ambas delegan en `_write_table` (helper interno), que vuelca la tabla como una **Excel Table real (ListObject)**, no como celdas sueltas: `money_cols`/`int_cols` (tuplas de índices 0-based sobre `headers`) escriben el valor como número real —no el texto ya formateado que trae la fila para pantalla, p. ej. "+67.40"; se reconvierte con `_to_number()`, que admite el "+" inicial y trata "" como celda en blanco— con formato `#,##0.00 €` o `#,##0` respectivamente (imprescindible para que la fila de totales pueda sumarlos: una Excel Table no suma texto). Añade una **fila de totales** (`totalsRowShown`) con fórmulas `SUBTOTAL` reales escritas en la hoja (openpyxl NO las genera solo al fijar `totalsRowFunction`, hay que escribirlas a mano): `=SUBTOTAL(103,Tabla[Col])` (COUNTA) en `count_col` (recuento de alumnos, vía DNI) y `=SUBTOTAL(109,Tabla[Col])` (SUM) en cada columna de `money_cols`; el resto de columnas quedan sin función. `_sanitize_table_name` da a cada tabla un `displayName` válido y único por libro (sin espacios, no empieza por dígito) a partir del nombre de hoja. Una Excel Table exige cabeceras no vacías y únicas: para el diff de Comparar Resumen, cuyas columnas "_fl" (flecha) llevan cabecera vacía EN PANTALLA a propósito (ver más abajo), `App._nombres_export_diff()` las renombra solo para la exportación como `"F_<columna anterior>"` (p. ej. la flecha de "Δ Acad." pasa a "F_Δ Acad."); Comparar Detalle no tiene ese problema (su columna Estado ya es texto normal). Los índices de `money_cols`/`int_cols`/`count_col` de cada tabla se precalculan una vez como constantes (`COL_DIFF_MONEY_COLS`/`COL_DIFF_INT_COLS`/`COL_DIFF_DNI_COL` en `App`, `COL_COMPDET_MONEY_COLS`/`COL_COMPDET_DNI_COL` a nivel de módulo) vía el helper `_col_indices(ids, *names)`: existe como función aparte (no una generator expression suelta en el cuerpo de la clase) porque una comprensión/generator dentro de un cuerpo de clase NO ve las variables de esa clase salvo en el iterable más externo (gotcha de scoping de Python 3) — como llamada de función normal, sí las ve.
- **`pdf_compare.py`** — motor de **comparación entre dos listados** (mismo informe en dos momentos: A = anterior, B = nuevo), sobre las `list[Registro]` de `parse_pdf`. No conoce tkinter ni Excel. `comparar(records_a, records_b) -> Comparacion`. Empareja por **Exped** (clave estable entre versiones del mismo curso), con el DNI como verificación normalizada (mismo comodín `U+FFFD` que `corregir_alineacion`); si un mismo Exped trae DNI distinto en A y B, la `FilaDiff` se marca `dni_distinto=True`. `FilaDiff` recoge un alumno presente en A y B, con deltas calculados (`delta_importe`/`delta_administrativo`/`delta_neto`) y el nº de recibos de cada lado (`num_refs_a`/`num_refs_b`); va a `modificados` si el importe cambió (I.Acad. bruto o I.Adm., comparados redondeados a céntimos) o a `iguales` si no (también `list[FilaDiff]`, con deltas 0, para poder listarlos en la UI). `Comparacion` agrega `modificados` e `iguales` (ambos ordenados alfabéticamente por nombre), `solo_a` (bajas), `solo_b` (altas), `pares` (los `(Registro_a, Registro_b)` emparejados de TODOS los alumnos en ambos listados — modificados + iguales —, para quien necesite comparar a nivel de `Referencia` sin reimplementar el emparejamiento; lo usa `_render_tablas_compdet` en Comparar Detalle), y los totales netos de cada fichero (`total_neto_a/_b`, `delta_total`). Los alumnos presentes solo en uno de los dos NO son filas de diff, pero se cuentan y devuelven para poder avisar (un importe puede "cambiar" porque el alumno causó baja). Verificado con las 2 muestras: totales netos cuadran (A=205 649,00 / B=220 943,66), 1643 modificados, 1 baja, 172 altas, 1 igual.
- **`Convert_PDF_Liquid_EP_to_Excel.py`** — UI tkinter (layout de 3 bloques + panel de configuración, plantilla del skill `tkinter-app-design`; `data_table.py` y `help_tooltips.py` están vendorizados junto a este archivo, misma fuente que en Corrector_Orientacion_PDF y Mailing_Personalizado). Bloque "Selección" = un único PDF + carpeta destino (sin cola); la carpeta destino empieza **vacía** al arrancar (no se pre-rellena desde el Registro) y se **autorrellena con la carpeta del propio PDF** al elegirlo (`_pick_pdf` hace `self._fuente2_var.set(os.path.dirname(path))`), aunque el usuario puede cambiarla después con "Seleccionar". Al elegir el PDF se lanza el **parseo** automáticamente (`_parsear()`/`_parsear_worker`, en un hilo aparte) — **ya no existe un botón "Ejecutar"**: parsear (automático, al elegir PDF) y guardar (explícito, botón aparte) son dos pasos independientes y nada se guarda en Excel sin que el usuario pulse guardar. Tabla 1 = "Vista previa (Detalle)" (columnas `Exp./DNI/Apellidos y Nombre/Referencia/F. Cobro/I.Acad./I.Adm./Rec./F. Pag.`, con `I.Adm.` justo detrás de `I.Acad.`); Tabla 2 = "Vista previa (Resumen)" (`Exped/DNI/Apellidos y Nombre/Rec./Importe/I.Acad./I.Adm.`, con `Rec.` = `len(r.referencias)` — nº de recibos/líneas de cobro del alumno; coincide en posición con la columna "Nº Refs." que `excel_export.py` ya escribía en la hoja Excel Resumen, aunque esta tabla de vista previa y esa hoja son código independiente). El botón **"💾 Guardar Excel"** (`_guardar_excel`) exporta a Excel los datos **ya parseados**: abre un diálogo `filedialog.asksaveasfilename` con la carpeta destino y un nombre propuesto (`{nombre_fichero}_{AAAAMMDD_HHMMSS}.xlsx`) precargados pero **editables** por el usuario (carpeta y/o nombre), y si se cancela no se guarda nada (log "Guardado cancelado"); el guardado (`_guardar_excel_worker`) corre en un hilo aparte para no bloquear la UI. El botón **"📂 Abrir Excel"** (`_abrir_excel_generado`) empieza **oculto** (`grid_remove()`) y solo se hace visible (`grid()`, que restaura la posición previa) tras el primer guardado con éxito de la sesión; abre el fichero generado (`self._ultimo_excel`), no la carpeta. Al terminar de grabar el Excel se muestra un **aviso modal de confirmación** (`_confirmar_grabacion`, `messagebox.showinfo`) con el nombre de archivo y la carpeta; al cerrarlo abre la carpeta destino si la opción de configuración "Abrir la carpeta destino al terminar" está activa. Este aviso solo salta al guardar desde el botón (las re-exportaciones tras revisar filas en `_aplicar_revision` solo regeneran el Excel si ya existe uno guardado en la sesión —`self._ultimo_excel`— y solo registran en el log, sin volver a preguntar por ruta ni mostrar el aviso). El bloque "Informe" tiene el log reducido a 4 líneas de alto (antes 6) para dejar más sitio a las tablas. La fuente de ambas tablas (`FONT_TABLA`/`FONT_TABLA_BOLD`) es un punto menor que `FONT_UI` (13 vs. 14), pasada explícitamente a `install_treeview_style()` y a los dos `DataTable(...)`.
- **Sincronización de selección por DNI entre Detalle y Resumen** (`_on_sel_detalle`/`_on_sel_resumen`/`_sync_select`/`_fila_activa`, mapas `_dni2iid_detalle` (dni → lista de iids) / `_dni2iid_resumen` (dni → iid), reconstruidos en cada `_load_tabla_detalle`/`_load_tabla_resumen`): seleccionar una fila en una tabla selecciona y centra (`DataTable.scroll_to`) la(s) fila(s) con el mismo DNI en la otra. Enganchado al binding `<<TreeviewSelect>>` de cada `DataTable` con `tree.bind(..., add="+")` para no pisar el binding interno de `DataTable` (franjas/tags de selección + contador "seleccionadas/total"). Guarda `self._sync_guard` para no entrar en eco entre las dos tablas mientras `_sync_select` aplica el cambio cruzado; se libera con `self.after_idle(...)` (no en el mismo tick) porque el propio `scroll_to` de la sincronización dispara eventos de scroll/selección que hay que poder ignorar durante la operación. `_aplicar_revision` reconstruye `_dni2iid_resumen` por completo tras corregir una fila (el DNI puede cambiar al separar DNI/Apellido): si no, la sincronización Detalle→Resumen se quedaba con la clave de DNI vieja para esa fila y dejaba de encontrarla (bug real detectado y corregido en la misma sesión que introdujo la sincronización). **Se probó además sincronizar por scroll** (activar automáticamente la primera fila visible de una tabla al desplazar su vista, vía un hook en `yscrollcommand`) y se **descartó a petición del usuario**: en uso real resultaba "un poco loco" (la vista se re-centraba sola en cada tick de rueda, compitiendo visualmente con el propio gesto de scroll), aunque los tests programáticos pasaban perfectamente — no reintentar este patrón (activar/reseleccionar automáticamente por scroll) sin acuerdo explícito primero.
- **Corrección de desalineación DNI/Apellido** (`corregir_alineacion` en `pdf_parser.py` + revisión en la UI): el PDF origen a veces desalinea la fila del alumno y el campo **DNI se "come" el inicio del apellido** (p. ej. `dni="DEUL5Z83KFMARTIN"`, `nombre=", KRÖDEL"` en vez de `dni="DEUL5Z83KF"`, `nombre="MARTIN, KRÖDEL"`). Señales de detección: `len(dni) > 10` (los DNI válidos miden 8-9; no hay ninguno entre 10 y 14 en las muestras) **o** el nombre empieza por coma. La heurística de separación aprovecha que el PDF va **ordenado por "Apellidos y Nombre"**: el fragmento comido es un sufijo alfabético del texto pegado, y se acepta el corte cuyo fragmento encaja como prefijo completo del apellido de un **vecino no sospechoso** (comparación normalizada — mayúsculas sin acentos — con `U+FFFD` como comodín, porque algunos nombres traen glyphs corruptos). No es fiable al 100 %, por eso cada fila queda **marcada** (`Registro.revisar=True`, con `dni_raw`/`nombre_raw`/`split_idx`) para validación manual. `corregir_alineacion` **no toca importes**, así que no altera el checksum de `IMPORTE TOTAL POR TASAS`; se llama **tras** `parse_pdf` (no dentro, para no cambiar el test de parseo). En las 2 muestras detecta y separa correctamente 2 filas cada una (`DEUL5Z83KF | MARTIN, KRÖDEL` y `21DK909549 | PÉREZ, RAYMOND`, corte en idx=10). Flujo de revisión en la UI (solo sobre la tabla **Resumen**, una fila por alumno): las filas marcadas se pintan de ámbar (`C_ROW_REVISAR`) en **ambas** tablas; la barra de título de Resumen muestra `⚠ Filas a revisar: N` + tres botones (`◀`/`▶` para saltar a la fila marcada anterior/siguiente centrándola, y `Revisar…` que abre un diálogo modal donde el texto pegado se separa **haciendo clic en el carácter donde empieza el apellido**, con vista previa en vivo y el contexto alfabético de los vecinos). Al aceptar: se aplica el corte, la fila se **desmarca**, la tabla se **reordena** alfabéticamente, se **actualiza el contador** y, si el dato cambió, se **regenera el Excel**. El Excel se exporta **ya corregido y sin marcar** (decisión del usuario): `excel_export.py` no necesita cambios, escribe lo que haya en cada `Registro`.
- **Panel Comparar Resumen (diff de dos PDF)** (`_show_comparar`/`_build_comparar_panel`/`_comparar_worker`/`_load_tabla_diff` + `pdf_compare.py`): botón **"⚖ Comparar Resumen"** en el bloque Selección que abre un **overlay a pantalla completa centrado** (mismo patrón que el panel de configuración, `place(relx=0.5, rely=0.5, anchor="center")`). Dentro: dos selectores de PDF (A = anterior, B = nuevo) — **sin botón "Comparar" manual**: al elegir el segundo PDF la comparación se lanza sola (`_pick_pdf_comparar`, igual que `_pick_pdf`; el botón se quitó por redundante, ya que reelegir cualquiera de los dos PDF con ambos ya puestos vuelve a disparar `_comparar_ejecutar`); un `Label` de resumen (solo los 4 contadores — Modificados/Solo en A/Solo en B/Sin cambios —, **sin el total neto de cada fichero**, que se quitó por abultar la barra sin aportar nada que la tabla ya no muestre); una fila de **filtros por Estado** («Mostrar: Altas / Bajas / Con cambios / Sin cambios», `_var_est_*` + `_refiltrar_diff`) — la tabla no lista solo modificados: también altas (`solo_b`), bajas (`solo_a`, con las columnas del lado ausente vacías, `_fila_solo`) y sin cambios (`iguales`), todo con ordenación alfabética global; y una **única tabla de diff** (`_tree_diff`, columnas `Exped/DNI/Apellidos y Nombre/Rec. A/Rec. B/[↕]/I.Acad. A/I.Acad. B/Δ Acad./[↕]/I.Adm. A/I.Adm. B/Δ Adm./[↕]/Δ Neto/[↕]/Estado`, importes alineados a la derecha) con filas coloreadas por tags: **verde** (`sube`, el neto sube en B), **rojo** (`baja`, el neto baja en B) y **ámbar** (`aviso`, mismo Exped con DNI distinto), con leyenda de colores debajo. La comparación corre en un hilo aparte (`_comparar_worker`) igual que la conversión. `pdf_compare.py` (motor, sin dependencias de tkinter/Excel) empareja por **Exped como clave primaria** con el DNI como verificación (normalización mayúsculas-sin-acentos con `U+FFFD` comodín, la misma de `corregir_alineacion`); `comparar(regs_a, regs_b)` devuelve una `Comparacion` (modificados/solo_a/solo_b/iguales + totales netos) y **no modifica** los `Registro`. A ambos listados se les aplica `corregir_alineacion` **antes** de comparar (no toca importes). Junto a la leyenda hay un **checkbox de filtro** "Ocultar filas donde solo cambia I.Adm." (`_var_comp_solo_acad` + `_refiltrar_diff`, re-filtra la última `Comparacion` sin re-parsear; el resumen muestra `(mostrados: N)` cuando está activo): existe porque en las dos muestras reales hay un **ajuste sistemático de −0,60 € en I.Adm. para casi todos los alumnos** (1.642 de 1.643 modificados) que sin el filtro inunda el diff y tapa los ~131 cambios reales de cobros. Las 4 columnas marcadas `[↕]` arriba (`rec_b_fl`/`d_imp_fl`/`d_adm_fl`/`d_neto_fl`, cabecera vacía) son columnas **estrechas contiguas** a Rec. B/Δ Acad./Δ Adm./Δ Neto que llevan **solo** la flecha ↑/↓ de esa columna: antes la flecha iba pegada al número dentro de la misma celda (p. ej. `"+67.40 ↑"`) y rompía la alineación a la derecha de la columna numérica; ahora el número va limpio (`_fmt_delta_num`, sin flecha) y la flecha sola en su columna (`_fmt_delta_arrow`), que `DataTable.autosize()` deja automáticamente estrecha (≈25 px, sin necesidad de `set_fixed_width`) al no tener cabecera ni contenido más ancho que un carácter. `_fmt_delta` (el formato combinado antiguo) se conserva tal cual porque lo sigue usando el panel Comparar Detalle (columna Estado de sus dos tablas, texto suelto sin problema de alineación). El título de la cabecera es «⚖ Comparar Resumen de dos liquidaciones (A = anterior, B = nuevo)» (antes «Comparar dos liquidaciones», sin distinguirlo del panel Comparar Detalle). La columna **Estado** de las filas modificadas ya no muestra el genérico "Con cambios": `_estado_cambios(f)` compone «Acad. ↑/↓» y/o «Adm. ↑/↓» según cuál de los dos importes (I.Acad. bruto, I.Adm.) cambió y en qué sentido, uniendo ambos con «/» si cambiaron los dos (p. ej. «Acad. ↑ / Adm. ↓»); las filas Alta/Baja/Sin cambios conservan su texto tal cual. Botón **"💾 Exportar Excel"** en la cabecera del panel (`_exportar_diff`/`_exportar_diff_worker`) exporta a un único `.xlsx` exactamente las filas visibles en `_tree_diff` en ese momento — respeta los filtros de Estado y el de "solo I.Adm." activos, vía `_filas_diff_visibles` (extraída de `_load_tabla_diff` para que tabla en pantalla y exportación nunca diverjan) — con `excel_export.export_rows_to_excel` (función genérica añadida a `excel_export.py`, headers+filas ya formateadas, sin depender de `Registro`, pensada para reutilizarse con otras tablas de la UI). El diálogo `asksaveasfilename` propone como carpeta la del propio ejecutable/script (`_exe_dir()`: `os.path.dirname(sys.executable)` si `sys.frozen`, si no el directorio del `.py`) y como nombre `Diff_Resumen_<AAAAMMDD_HHMMSS>.xlsx`, editable por el usuario antes de guardar (mismo patrón que "Guardar Excel" de la ventana principal); si se cancela, no se exporta nada. Verificación del motor: `comparar(ra, ra)` debe dar 0 modificados/solo_a/solo_b y Δ 0.0; y con las dos muestras, `modificados + iguales + solo_X == len(registros_X)` en ambos lados. **Nota**: `_tree_diff` NO participa en el auto-ajuste de fuente (`_autofit_tablas` solo toca Detalle y Resumen); comparte el estilo ttk `"Treeview"`, así que hereda el tamaño de letra que haya dejado el último auto-ajuste, pero sus columnas se miden con `FONT_TABLA` fijo — interacción cosmética menor, no rompe nada.
- **Panel Comparar Detalle (dos tablas lado a lado)** (`_show_comparar_det`/`_build_comparar_det_panel`/`_comparar_det_worker`/`_load_tablas_compdet`): botón **"⚖ Comparar Detalle"** en el bloque Selección (debajo de "⚖ Comparar Resumen"), mismo overlay a pantalla completa y misma mecánica de selección A/B (vars propias `_compdet_a_var`/`_compdet_b_var`, al elegir el segundo PDF se lanza solo; parseo en hilo aparte con `corregir_alineacion` antes de mostrar). El panel **no tiene botón "Comparar" propio** (se quitó por inútil: `_pick_pdf_comparar_det` ya lanza `_comparar_det_ejecutar()` automáticamente en cuanto ambos PDF están elegidos, así que el botón nunca aportaba nada que no hiciera ya la selección). **No hay diff agregado por alumno**: muestra las tablas de Detalle de ambos PDF **lado a lado** (A izquierda, B derecha), cada una en un bloque con cabecera morada `BG_TAB1` + **última fecha de cobro** + contador (helper `_bloque_tabla_detalle`, devuelve `(DataTable, Label)`; la fecha se calcula con `_ultima_fecha_cobro` — la `Referencia.fecha` más reciente entre TODOS los registros de ese lado, `regs_a`/`regs_b` sin filtrar por el checkbox — y se recalcula en cada `_render_tablas_compdet`), con las **mismas filas base que la vista previa principal** (una por cobro + una de Imp.Adm. por alumno) más una columna **Estado** propia del panel (`COL_COMPDET_IDS/NAMES = COL_DETALLE_*[:7] + ("estado",)`; decisión del usuario no llevar Rec./F. Pag.). `_config_tabla_detalle` centraliza anclajes (incl. `estado` centrado) + tag `revisar` para las tres tablas tipo Detalle, aplicando solo los anclajes de columnas presentes (`set_anchor` revienta con columnas inexistentes). Un `Label` de resumen muestra pág./alumnos/neto de cada PDF y el Δ neto. **Estas tablas SÍ participan del auto-ajuste**: `_autofit_compdet` (mismo algoritmo que `_autofit_tablas`) se lanza tras cargar; `_apply_table_font` re-mide también estas dos tablas si existen (comparten el estilo ttk `"Treeview"`); el handler de `<Configure>` re-ajusta el panel si está visible con datos (si no, las tablas principales); y al **cerrar** el panel (`_hide_comparar_det`) se re-ejecuta `_autofit_tablas` para devolver a las tablas principales su tamaño óptimo.

Tras rellenar las dos tablas (`self.after(0, self._autofit_tablas)` al final de `_ejecutar_worker`), el auto-ajuste elige **un único tamaño compartido por ambas tablas**: el mayor de la banda `[mín, máx]` con el que **las dos** quepan enteras a lo ancho de su recuadro sin scroll horizontal. Como es compartido, **manda la tabla más restrictiva** (la que tiene menos hueco relativo — a menudo Resumen, que va en un recuadro más estrecho); si ni el mínimo de la banda cabe, se aplica el mínimo y aparece scroll horizontal (fallback honesto, respeta la banda). El algoritmo (`DataTable.fit_font_size(smin, smax, avail_px)`) mide solo la **celda representativa** por columna (la más ancha; el argmax es estable al cambiar de tamaño, se localiza en una pasada midiendo únicamente las cadenas más largas por nº de caracteres), así que el coste es cols×tamaños, no filas×tamaños — instantáneo con miles de filas. `_apply_table_font(size)` reconfigura el estilo ttk **compartido** `"Treeview"` (fuente + `rowheight=int(size*2.4)+1`) y llama a `set_measure_fonts`+`autosize()` en las dos tablas para que las columnas vuelvan a cuadrar. Además, un **handler de `<Configure>` con debounce (200 ms)** re-ejecuta el auto-ajuste cuando cambia el **ancho** de la ventana (al terminar de maximizarse tras el arranque, o si el usuario la redimensiona), comparando `winfo_width()` para no reaccionar a cambios de alto ni entrar en bucle (aplicar la fuente no cambia el ancho de la ventana). Guardar la configuración vuelve a auto-ajustar si hay datos cargados. **Decisión de diseño abierta**: tamaño *compartido* (uniforme entre las dos tablas, más simple y sin tocar estilos ttk por-widget) en vez de *independiente por tabla* — si se quisiera que cada tabla maximice su propio tamaño habría que darle a cada `Treeview` su estilo ttk propio (copiar layout incl. `DT.RowSep` + limpiar el map `selected`), más frágil en el componente vendorizado. Estas adiciones a `data_table.py` (`fit_font_size`, `set_measure_fonts`) **no se han replicado aún** a `Corrector_Orientacion_PDF`.
- **Ancho y alineación de las tablas**: ninguna columna usa `set_fixed_width` — el ancho de cada columna en `DataTable.autosize()` (`data_table.py`) es exactamente el valor más ancho (cabecera o dato) más el padding, sin repartir hueco sobrante como aire extra entre columnas (si se usara `set_fixed_width` en el futuro, actúa como MÍNIMO garantizado, nunca trunca). - **Tags "sticky" en `data_table.py`** (añadido aquí para la revisión de desalineación, **sin replicar aún** a `Corrector_Orientacion_PDF`): los tags de fila que no son de franja (`row_a`/`row_b`) se guardan en `self._sticky` y **sobreviven a la ordenación** — `_restripe()` respeta el tag sticky en vez de repintar la fila como franja, para que las filas marcadas (`revisar`) no pierdan su color al reordenar. `load()` ahora **devuelve la lista de iids** insertados (para mapear iid→`Registro`), y hay utilidades nuevas: `scroll_to(iid, center=True)` (centra una fila en la vista), `sort(col_id, reverse=False)` (ordenación determinista, no alterna sentido como el clic en la cabecera), `set_values(iid, values)` y `unmark(iid)` (actualizar/desmarcar una fila en sitio sin recrearla).

## Formato del PDF de entrada (importante si se toca `pdf_parser.py`)

Informe paginado, cabecera/pie repetidos en cada página, con la fila de columnas `Exped | Dni | Apellidos y Nombre | Referencia | Fecha Cobro | Importe Cobrado | Plazo | Forma Pago`. Por cada alumno:

```
<Exped>  <Dni>  <Apellidos y Nombre>
<Referencia 13 dígitos>  <dd/mm/aaaa>  <Importe>  <Plazo>  <Forma Pago>   (1..n líneas)
Importe:          <suma de los importes cobrados>
Administrativo:   <gastos administrativos>
Importe Total :   <importe neto> €        (puede venir en blanco)
```

Al final del documento: `IMPORTE TOTAL POR TASAS : <importe> €` (gran total).

### Peculiaridades reales del PDF (verificadas con PyMuPDF, no son artefactos de extracción)

- **Usar `get_text("text", sort=True)`, no el orden de lectura por defecto.** Sin `sort=True`, la cabecera de columnas sale mezclada (los fragmentos de texto se leen en el orden en que se dibujaron en el PDF, no en orden visual). Con `sort=True` el texto sale ya alineado por líneas visuales y es directamente parseable por regex — no hizo falta extracción por coordenadas (`get_text("words")`) pese a que ese fue el plan inicial.
- **Discriminador Exped vs Referencia**: la Referencia de cobro son siempre 13 dígitos (empieza por el año, p. ej. `2025985284015`); el Exped nunca llega a esa longitud (1-4 dígitos en los PDF de muestra). Es la clave para distinguir la línea de cabecera de alumno de una línea de cobro sin ambigüedad.
- **"Importe Total" en blanco**: en ~0,6 % de los registros el PDF no imprime el valor de esa celda (el resto de campos sí están bien). No se ha encontrado un patrón que lo explique (no depende de tener 1 o varias líneas de referencia). Por eso `Registro.importe_neto` se calcula siempre, no se lee directamente.
- **Ñ/tildes corruptas en el propio PDF** (no es un problema de extracción): algunos nombres traen glyphs sin mapeo Unicode válido en la fuente embebida del PDF origen. Ejemplos reales extraídos con `fitz`: `"IVA#EZ OLCINA, MONICA"` (Ñ → `#`) y `"CARDONA VALENCIA, BEGO<U+FFFD>A"` (Ñ → carácter de reemplazo). El conversor no intenta "arreglar" estos nombres — se exportan tal cual vienen, porque no hay forma fiable de saber qué carácter faltaba.
- **DNI heterogéneo**: NIF, NIE (`X`/`Y`/`Z` + dígitos + letra), pasaporte extranjero con letras, y algunos con el mismo tipo de corrupción de fuente que los nombres. Se trata siempre como texto libre, sin validar formato.
- **Importes negativos (devoluciones, `Forma Pago` = 92)**: algunas líneas de referencia y algunos totales traen importe negativo (p. ej. `-34,60` o `Importe Total : -9,18 €`). Las regex `_REF_RE` y `_TOTAL_RE` deben admitir un `-?` opcional delante del número — sin él, esas líneas no matchean ninguna regex y se descartaban en silencio (bug detectado y corregido: 25 líneas de referencia y 3 "Importe Total" se perdían en el segundo PDF de muestra). Este caso **no lo detecta** el checksum de `IMPORTE TOTAL POR TASAS`, porque `importe_neto` se calcula desde las líneas `Importe:`/`Administrativo:` (que ya traen el neto correcto), no reconstruyendo desde las líneas de referencia — por eso, al tocar `_REF_RE`/`_TOTAL_RE`, verificar además que no queden "líneas no reconocidas" (barrido línea a línea, no solo el total agregado).
- El segundo PDF de muestra (`_237_1450473_ltimastasas202526.pdf`, 228 páginas, 1816 registros, total neto 220.943,66 €) sigue el mismo layout y lo parsea el mismo código sin cambios de estructura (motivó el fix de importes negativos anterior).
